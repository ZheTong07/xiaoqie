## 二、已完成

### 2.1 M0 · v1 本地版（已归档）

产品功能在这一阶段全部成型，v2 只是把存储换成云端，界面与交互没有重做：

- 时间线浏览：`occurred_at` 降序，同一天按 `created_at` 降序。
- 记录 CRUD：日期、标题、正文、地点、情绪标签、里程碑、归属（我 / ta / 共同）。
- 情绪标签：8 个固定词表 + 自定义追加。
- 媒体：多选照片 / 视频；照片压缩到长边 1920px、JPEG 质量 0.85；视频不压缩；
  列表最多展示 4 张缩略图 + `+N`；灯箱支持图片放大、视频播放并接续列表进度。
- 随机回顾：优先抽里程碑，没有则全量随机。
- 设置：软件标题、纪念日前缀、纪念日，实时计算「在一起 N 天」。
- 数据备份：单文件 JSON（记录 + 媒体 DataURL + 设置），按 ID 合并导入。
- PWA：`manifest.json` + `sw.js` 应用外壳缓存。
- 视觉：线条小狗风格（纯黑线条、白 / 淡黄 / 淡粉、最大宽度 720px、动效 120–200ms）。

> 本阶段使用的 IndexedDB（`xiaoqie-entries` / `xiaoqie-media`）已**废弃且不再读写**，
> 遗留数据不迁移（已确认是测试数据）。详见 CLAUDE.md「已废弃」章节。

### M2 · 账号与权限（P0，6–9 人天）

目标：把安全边界从「谁拿到 key」变成「谁登录了、属于哪段关系」。

| ID | 任务 | 说明 | 估时 |
|---|---|---|---|
| T2-1 | 确定登录方式 | 推荐 Supabase Auth 邮箱魔法链接（无密码、无验证码成本）；备选邮箱+密码、微信第三方（成本高） | 0.5 |
| T2-2 | 登录页与会话 | `auth.js` 页面模块、会话持久化、未登录跳登录、退出登录 | 1.5 |
| T2-3 | 关系数据模型 | `relationships(id, name, anniversary_date, created_by, created_at)`、`relationship_members(relationship_id, user_id, role, joined_at)` | 1 |
| T2-4 | 现有数据归属 | 把 `cloud-rel-1` 的 1 条记录迁到第一条真实 relationship；`CLOUD_SCOPE` 改为从会话注入 | 1 |
| T2-5 | 邀请加入 | 邀请码 / 邀请链接，对方登录后加入同一 relationship（成员上限 2） | 1.5 |
| T2-6 | 重写 RLS | `entries` / `media` 按「当前用户是关系成员」过滤；`storage.objects` 按路径首段（关系 ID）限制；去掉 `anon` 全开策略 | 1.5 |
| T2-7 | `owner_id` 改为真实用户 | 写入时取 `auth.uid()`，不再用 `local-user` | 0.5 |
| T2-8 | 设置上云（可选） | 标题 / 纪念日随 relationship 同步，localStorage 仅作缓存 | 1 |
| T2-9 | 回归测试 | 未登录不可读写；A 看不到 B 的关系；跨关系 ID 直接访问被拒 | 1 |

**风险**：RLS 写错会导致「所有人都看不到」或「所有人都能看到」，必须用两个测试账号做矩阵验证；
迁移现有数据前先导出备份。

**完成定义**：未登录访问任何数据接口返回 401/空；两个账号的数据完全隔离；现有记录不丢。

## 五、技术债与风险清单

| # | 风险 | 影响 | 处理建议 | 优先级 |
|---|---|---|---|---|
| 1 | RLS 对 `anon` 全开放 | 拿到 key 的人可读写全部数据 | M2 彻底收紧 | **P0** |
| 2 | publishable key 硬编码在前端 | 本身可公开，但配合风险 1 就是敞口 | 随 M2 收口；**绝不放入 service_role** | P0 |
| 3 | 列表全量加载 | 记录变多后首屏变慢、流量增加 | M5 T5-1 分页 | P1 |
| 4 | 缩略图直接用 1920px 原图 | 一屏 4 张图 ≈ 数 MB | M5 T5-2 | P1 |
| 5 | 删除后 CDN 缓存 1 小时 | 旧 URL 短期内仍可访问 | 已从 1 年改为 1 小时；如需更快只能接受回源成本（`cacheControl: 0`） | P2 |
| 6 | 无自动化测试仓库 | 回归靠手测，改动风险高 | 把 e2e / backup 脚本产品化（Node + `@supabase/supabase-js`，独立测试项目） | P1 |
| 7 | 设置只在 localStorage | 换设备后标题 / 纪念日丢失 | M2 T2-8 | P2 |
| 8 | Service Worker 手改版本号 | 忘记 +1 会导致用户看到旧页面 | 发布清单里固化，或加构建脚本自动哈希 | P2 |
| 9 | 备份全量 DataURL | 媒体多时文件巨大、导出慢 | M4 T4-4 | P2 |
| 10 | 无错误监控 | 线上报错只能靠用户描述 | 可选接入 Sentry（注意隐私，照片绝不外传） | P3 |
| 11 | Supabase 免费额度 | 存储 / 出站流量有上限 | 上线前估算：按 1000 张 × 300KB ≈ 300MB 存储；关注 egress | P2 |

## 六、每个阶段的完成定义（DoD）

任何阶段合入前必须同时满足：

1. **分层约束**：页面层没有直接调用 Supabase；`mediaStore` 不依赖 `repository`；
   `repository` / `mediaStore` 对外只返回普通 JS 对象。
2. **失败路径**：网络失败、权限失败、文件过大都有中文提示，不出现英文报错或白屏。
3. **真机验证**：浏览器验收清单通过；涉及多端的阶段必须双设备实测。
4. **文档同步**：CLAUDE.md 与 `docs/development-plan.md` 更新；表结构变更写进 `supabase/schema.sql`。
5. **数据安全**：改动涉及 RLS 时，必须用两个账号验证隔离；涉及删除时，验证行与对象都被清理。
6. **无测试残留**：自动化测试跑完，云端不留测试记录与文件。
